# Research: Сайт бара с меню и клиентским кабинетом

**Feature**: [spec.md](./spec.md) | **Date**: 2026-07-23

Источник решений по стеку — прямой выбор пользователя (Next.js, PostgreSQL, собственная аутентификация, VPS). Остальные пункты — технические решения, необходимые для реализации FR из спецификации, но не заданные явно.

## 1. Фреймворк и архитектура

- **Decision**: Next.js (App Router) как единый full-stack проект — серверный рендеринг публичных страниц (меню, главная, контакты) + API-роуты (Route Handlers) для личного кабинета, лайков, поиска.
- **Rationale**: Один проект вместо связки backend+frontend упрощает деплой на один VPS-процесс; SSR даёт быструю первую отрисовку меню и лучшую индексацию (важно для локального бизнеса — поиск бара по названию/адресу).
- **Alternatives considered**: Node.js/Express API + отдельный SPA (React/Vue) — отклонено, лишняя инфраструктурная сложность для проекта такого размера; статический сайт + отдельный бэкенд — отклонено, личный кабинет требует SSR/аутентификации на сервере.

## 2. Язык

- **Decision**: TypeScript.
- **Rationale**: Модель данных (меню, чеки, бонусы) выигрывает от типобезопасности; стандарт для новых Next.js проектов.
- **Alternatives considered**: JavaScript — отклонено, выше риск ошибок в расчётах бонусов/цен без типов.

## 3. База данных и доступ к данным

- **Decision**: PostgreSQL + Prisma ORM.
- **Rationale**: PostgreSQL выбран пользователем; Prisma даёт типобезопасные запросы из TypeScript, миграции из коробки, хорошо ложится на реляционную модель (пользователи → чеки → позиции чека, бонусные операции).
- **Alternatives considered**: Sequelize/TypeORM — рабочие альтернативы, но менее удобная типизация под Next.js/TS сегодня; сырой SQL — отклонено, избыточные ручные миграции для старта проекта.

## 4. Аутентификация и восстановление пароля

- **Decision**: Собственная реализация на базе Auth.js (NextAuth): единственный способ входа — Credentials Provider, который верифицирует Telegram Login Widget (HMAC-SHA256 подпись + свежесть `auth_date`, см. `lib/telegram-auth.ts`), без пароля и без отдельной формы регистрации. Сессия — JWT в httpOnly cookie. Если у Telegram-пользователя не указан телефон, система запрашивает его отдельным шагом после первого входа (нужен для привязки чеков). Telegram-вход хранится напрямую на модели `User` (поля `telegramId`/`telegramUsername`), аккаунт создаётся автоматически (`upsert` по `telegramId`) при первом входе.
- **История решения**: изначально планировался email/телефон+пароль как основной способ с Google/Apple OAuth как альтернативой; затем Google/Apple заменены на Telegram; затем (2026-07-23) email/телефон+пароль и восстановление по SMS убраны полностью — Telegram остался единственным способом входа по решению владельца.
- **Rationale**: Соответствует явному выбору «своя реализация» из спецификации; Auth.js берёт на себя безопасную работу с сессиями/cookie. Google/Apple OAuth изначально рассматривались, но заменены на Telegram Login Widget по решению владельца (регистрация без OAuth-приложений Google/Apple, через уже привычный пользователям Telegram) — верификация делается серверным HMAC-SHA256 по `bot_token` (см. `lib/telegram-auth.ts`), без необходимости в OAuth-адаптере или redirect-флоу.
- **Alternatives considered**: Полностью ручная реализация JWT — отклонено, больше поверхности для ошибок безопасности без выигрыша в контроле; Supabase/Firebase Auth как основной механизм — отклонено пользователем явно; Google/Apple OAuth — отклонено пользователем в пользу Telegram; вход через Instagram — отклонено как непрактичное (требует Meta App Review и верификации бизнеса для базовых прав входа).

## 5. SMS-провайдер для восстановления пароля (удалено)

- **Статус**: Больше не актуально. Восстановление пароля по SMS и сам `lib/sms-sender.ts` удалены 2026-07-23 вместе с email/телефон+паролем — восстанавливать нечего, единственный способ входа Telegram. Если в будущем понадобится SMS для других целей (например, уведомления о бонусах), это отдельная фича с новым `research.md`-разделом, а не восстановление того, что здесь описывалось.

## 6. Хранение фотографий позиций меню

- **Decision**: Локальное файловое хранилище на VPS (папка `public/uploads/menu/`, доступ по прямому URL через Next.js static serving) за интерфейсом `ImageStorage`, с возможностью позже переключиться на S3-совместимое хранилище (например, Cloudflare R2) без изменения остального кода.
- **Rationale**: VPS уже выбран как хостинг — локальный диск не требует дополнительных внешних сервисов/затрат на старте; абстракция сохраняет путь к масштабированию.
- **Alternatives considered**: S3/R2 с самого начала — отклонено как избыточное для старта; хранение изображений в БД (bytea) — отклонено, хуже для раздачи статики и бэкапов.

## 7. Защита лайков от накрутки (анонимные посетители)

- **Decision**: Идентификатор посетителя в подписанной cookie (`visitor_id`, генерируется при первом визите), уникальное ограничение в БД на пару `(visitor_id, menu_item_id)`, повторный клик — toggle (снятие лайка).
- **Rationale**: Не требует регистрации (по спецификации лайки доступны анонимно), простая и надёжная защита от case «один клик — много лайков»; полноценная защита от подмены cookie не требуется для MVP.
- **Alternatives considered**: Ограничение по IP — отклонено, ненадёжно для общего Wi-Fi/NAT (несколько гостей за одним IP в баре); отсутствие защиты — отклонено, легко накручивается.

## 8. Формирование чеков и начисление бонусов

- **Decision**: Для v1 чеки и бонусные операции создаются вручную через внутренний административный интерфейс/скрипт персоналом заведения (привязка чека к гостю — по номеру телефона), а не через автоматическую интеграцию с кассой/POS. Бонусы начисляются как процент от суммы чека (процент — настраиваемый параметр), рассчитывается и сохраняется как отдельная `BonusTransaction` при создании чека.
- **Rationale**: Соответствует допущению из спецификации («интеграция с конкретной POS-системой — вопрос последующего планирования»); позволяет запустить личный кабинет и программу лояльности до появления полноценной кассовой интеграции.
- **Alternatives considered**: Реалтайм-интеграция с конкретной POS/кассовой системой — отклонено на этом этапе, требует выбора конкретной кассы заведением (отдельная будущая фича/интеграция).

## 9. Развёртывание

- **Decision**: VPS с Node.js (процесс под PM2) за Nginx как reverse proxy/TLS-терминатором, PostgreSQL на том же или соседнем сервере.
- **Rationale**: Соответствует выбору «обычный VPS»; PM2 + Nginx — стандартная, хорошо документированная связка для Next.js вне serverless-платформ.
- **Alternatives considered**: Docker Compose (Next.js + Postgres + Nginx в контейнерах) — хорошая альтернатива для воспроизводимости, можно принять на этапе задач/реализации как способ упаковки того же решения, не меняет архитектуру.
